# S3 image storage

The storage module is in `src/s3client`:

- `S3ClientBase` is the service-facing interface.
- `S3Client` saves images through `userver::s3api::Client`.
- `S3ClientComponent` builds the SDK connection and authenticator from config.
- `S3ClientConfig` holds endpoint and bucket only, without credential copies.
- `SaveImageResponse` contains `success`, `error_message`, and `url`.

## Upload contract

`SaveImage(contents, storage_key, content_type)` accepts raw image bytes,
including embedded zero bytes. It does not accept base64 or a local file path.
The existing multipart handler extracts the `file` field; the media service
validates the image and generates `images/<uuid>.<extension>` before saving
that exact key to the database and S3. Pass a full canonical MIME type:
`image/jpeg`, `image/png`, `image/webp`, or `image/gif`, not an extension.

This adapts the reference implementation: the client does not generate another
`imgs/` prefix or append an extension to a key already generated by the service.
Reusing a key replaces the current object. The caller validates actual image
contents and access permissions. Storage keys have a maximum of 1024 bytes,
contain only ASCII letters, digits, `/`, `-`, `_`, and `.`, and cannot contain
empty, `.` or `..` path segments.

Invalid upload arguments and storage errors return `success=false`, a safe error
message, and an empty URL. Task cancellation propagates. Invalid constructor
configuration throws `std::invalid_argument` before the client can be used.
A successful upload returns `https://<bucket>.<endpoint>/<storage_key>`.
This is an object address, not a signed URL or a grant of public access;
bucket permissions and provider support determine whether it is readable.
The media service returns `media_id` and a signed `image_url` valid for one hour.
Reading a quiz renews its image links. Keep the bucket private.

## Environment

`make start-debug` loads `.env`. For a direct executable launch, export the
variables into that process environment first. Use the names in `.env.example`:

```dotenv
S3_ENABLED=true
S3_ENDPOINT=storage.yandexcloud.net
S3_BUCKET=your-bucket-name
S3_ACCESS_KEY_ID=your-access-key
S3_SECRET_ACCESS_KEY=your-secret-key
```

Do not commit credentials. Uploads are disabled by default. Missing credentials
or a bucket cause startup to fail when enabled. The endpoint is a DNS host,
without scheme, port or path. The component uses HTTPS, a 10-second timeout,
and userver 3.1's `AccessKey` authenticator, as in the reference implementation.
Provider authentication compatibility must be checked against the actual bucket.

## Checks and remaining integration

Build `RumpelQuiz` and `RumpelQuiz_unittest` in the development container, then
run `build-debug/RumpelQuiz_unittest --gtest_filter=S3Client.*`.
Tests use the SDK mock and never upload to a real bucket. They cover binary
contents, string-view boundaries, MIME types, key limits, URLs, failures,
retries, replacement, cancellation, and invalid/disabled clients.
Functional tests explicitly disable S3 even if the host exports S3_ENABLED.

`POST /v1/media/images` accepts exactly one multipart field `file` from an
authenticated teacher or university administrator. PNG, JPEG and WebP are
decoded before upload (5 MiB, 8192 pixels per side, 12 megapixels maximum).
The S3 client also accepts GIF, but the media endpoint deliberately does not.
The media row becomes ready only after storage confirms the upload.
Quiz saves verify that all referenced images are ready and belong to the author.
The migration is `postgresql/migrations/005_quizzes_media.sql`.

Pending upload reconciliation and cleanup of unattached ready images are not
implemented. Removing an image from a quiz removes its reference, not the S3
object. Functional tests disable external S3 and check the resulting 503.
