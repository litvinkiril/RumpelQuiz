# Факультеты, направления и область полномочий

## Применение к существующей базе

Перед запуском обновлённого приложения откройте в pgAdmin Query Tool файл
`postgresql/migrations/004_university_structure.sql` и выполните его целиком.
Миграция рассчитана на базу после `003_education.sql`. Она не создаёт факультеты
или направления за пользователя и не удаляет существующих людей, роли и группы.
Повторное выполнение допускается. При ошибке выполните `ROLLBACK;`, устраните
причину и повторите весь скрипт.

Для новой базы `postgresql/schemas/db_1.sql` уже содержит ту же структуру.
Тест проверяет совпадение общего блока схемы и миграции.

## Структура

- `education.faculties`: факультет одного вуза.
- `education.programs`: направление одного вуза.
- `education.faculty_programs`: факультеты направления, связь многие-ко-многим.
- `education.study_groups.program_id`: одно направление группы.
- `education.memberships.admin_scope`: `university` или `faculties` для админа,
  `NULL` для остальных ролей. Значения по умолчанию нет.
- `education.admin_faculties`: факультеты, которыми управляет конкретное
  администраторское членство. Это полномочия, а не место работы сотрудника.

Составные внешние ключи запрещают связи между разными вузами. Направление должно
иметь хотя бы один факультет к завершению транзакции. Создавайте направление и
связи с его факультетами внутри одного `BEGIN ... COMMIT`. Последнюю связь нельзя
удалить, не назначив другой факультет или не удалив само направление.

Пока существующие группы не распределены, `program_id` допускает `NULL`.
После распределения можно отдельной миграцией установить `NOT NULL`; текущая
миграция этого не делает. Факультеты группы определяются через её направление.

## Права

Существующим администраторам при первом запуске миграции назначается
`admin_scope = 'university'`, включая неактивные членства (статус не меняется).
Повторный запуск миграции никого не повышает и не активирует.

Для нового администратора область нужно указать явно. Старый SQL импорта
администраторов без `admin_scope` теперь будет отклонён ограничением БД.

Администратор области `faculties` может управлять несколькими факультетами.
Пустой список назначений не предоставляет административных полномочий.
Группами совместного направления может управлять администратор любого из его
факультетов. Группами без направления — только администратор всего вуза.
Неактивное членство не даёт полномочий даже при сохранённых назначениях.

`EducationService::CanManageUniversity/CanManageFaculty/CanManageGroup` принимают
транзакцию вызывающего кода: будущие обработчики изменений должны проверять
полномочия в транзакции самого изменения. Проверка ресурса включает его вуз.
Простая проверка наличия роли `admin` не заменяет эти проверки для записи.

Профиль возвращает `admin_scope` в каждой позиции. Интерфейс различает
администратора факультетов и администратора вуза. Этот этап не добавляет формы
создания факультетов, направления и назначения полномочий. Общий поиск людей
с фильтрами — отдельное изменение; существующий список администраторов сохранён.

## Проверка после миграции

```sql
SELECT role, admin_scope, status, COUNT(*)
FROM education.memberships
GROUP BY role, admin_scope, status
ORDER BY role, admin_scope, status;

SELECT id, university_id, name
FROM education.study_groups
WHERE program_id IS NULL;
```

Текущую пользовательскую базу автоматические тесты не изменяют: схемы,
миграция, ограничения и выдача профиля проверяются в отдельной тестовой БД.
